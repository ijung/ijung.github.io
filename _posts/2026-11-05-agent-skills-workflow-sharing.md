**난이도: 입문 — AI 에이전트나 스킬을 처음 접해도 읽을 수 있습니다.**

## 세 줄 요약

- Anthropic은 **2026년 10월 22일**, 에이전트의 전문 지식·업무 절차를 담는 공개 표준 Agent Skills를 Agentic AI Foundation(AAIF)에 기부한다고 발표했습니다.<a href="#source-1">[1]</a> 이번 글은 발표 재소개에 그치지 않고 구성과 활용의 의미를 설명합니다.
- 스킬의 기본 단위는 **`SKILL.md`가 들어 있는 폴더**이며, 필요하면 스크립트·참고 문서·자료를 함께 둘 수 있습니다.<a href="#source-2">[2]</a>
- **분석:** 공유하기 쉬워지는 것은 업무 절차이지 실행 권한이 아닙니다. 설치하기 전에 무엇을 읽고 실행하고 전송할 수 있는지 확인하고, 다른 플랫폼에서도 같은 결과가 나오는지는 따로 검증해야 합니다.

> 확인 기준: **2026년 11월 5일(KST)**. Anthropic 발표와 Agent Skills 공식 규격·구현 안내를 확인했습니다. 이 글의 구성 예시는 설명용이며 실제 스킬로 설치·실행하지 않았습니다. 플랫폼별 호환성과 보안성을 직접 시험한 리뷰가 아닙니다.

## 1. 무엇을 공유하는 표준입니까?

Anthropic은 스킬을 특정 작업이나 도메인을 에이전트에게 알려주는 `SKILL.md`와 필요한 스크립트·참고자료를 담은 폴더로 설명합니다.<a href="#source-1">[1]</a> 단순히 일반 지식을 묻는 것과 달리, 실제 업무에는 **어떤 순서로 처리하고 무엇을 확인해야 하는지**에 관한 절차 지식이 필요했다는 것이 개발 배경입니다.<a href="#source-1">[1]</a>

기부 대상으로는 Agent Skills의 이름·로고, GitHub 조직, `agentskills.io` 도메인이 명시됐습니다.<a href="#source-1">[1]</a> 표준을 사용하거나 기여하기 위해 AAIF에 가입할 필요는 없다는 설명도 있습니다.<a href="#source-1">[1]</a>

**분석:** 이 변화의 의미는 “어느 회사의 에이전트가 더 잘 답합니까?”와 별도로, 업무 지식을 어떤 형식으로 보관하고 공유할지 논의할 기반이 넓어진다는 데 있습니다. 재단이 관리한다고 해서 개별 스킬의 코드나 작성자를 모두 검증해 준다는 뜻으로 받아들여서는 안 됩니다.

## 2. 구성은 단순하지만, 무엇을 담을지는 중요합니다

규격은 폴더 안에 최소한 `SKILL.md`를 두고, 파일을 **YAML frontmatter와 Markdown 본문**으로 구성하도록 정합니다.<a href="#source-2">[2]</a> `name`과 `description`은 필수이며, 본문에는 단계별 지침·입출력 예시·주의할 경우 등을 적을 수 있습니다.<a href="#source-2">[2]</a>

선택적으로 `scripts/`에는 실행 코드, `references/`에는 참고 문서, `assets/`에는 템플릿·자료 등을 둘 수 있습니다.<a href="#source-2">[2]</a> 코드가 반드시 있어야 스킬이 되는 것은 아닙니다.<a href="#source-2">[2]</a>

다음은 **설명용 구성 예시**입니다. 설치 가능한 배포본이나 실제 실행 기록은 아닙니다.

```text
note-review/
├── SKILL.md
└── references/
    └── checklist.md
```

`SKILL.md`의 내용은 다음처럼 생각할 수 있습니다.

```markdown
---
name: note-review
description: Review user-provided notes and draft action items.
---

# 메모 검토

1. 사용자가 제공한 메모에서 결정과 제안을 구분합니다.
2. 할 일·담당자·기한을 정리하고, 없는 정보는 추측하지 않습니다.
3. references/checklist.md를 참고해 누락을 확인합니다.
4. 결과는 초안으로 반환하고 외부 전송은 하지 않습니다.
```

폴더 이름과 `name`을 맞추고 필수 메타데이터 뒤에 본문을 두는 기본 구조는 규격에 따른 것입니다.<a href="#source-2">[2]</a> 메모 검토 절차와 전송 금지 문구는 이 글이 만든 예시이며, **이 문구만으로 실행 환경의 접근제어가 구현되는 것은 아닙니다.**

**분석:** 반복해서 긴 요청을 쓰는 대신 검토 순서와 누락 처리 기준을 문서로 남길 수 있다는 점이 중요합니다. 다만 지침이 실제로 지켜지는지, 참고 파일이 올바른지, 결과가 원자료와 맞는지는 별도 확인이 필요합니다.

## 3. 재사용과 실행 권한은 서로 다른 층입니다

규격의 `allowed-tools`는 선택적·실험적 필드이며, 지원 방식이 에이전트 구현에 따라 다를 수 있다고 명시돼 있습니다.<a href="#source-2">[2]</a> 공식 구현 안내도 파일을 직접 읽는 방식과 전용 활성화 도구를 사용하는 방식을 구분하며, 전용 도구가 권한 확인이나 사용자 동의를 수행할 수 있다고 설명합니다.<a href="#source-3">[3]</a>

따라서 스킬의 설명을 읽는 것, 스크립트를 실행하는 것, 외부 시스템에 결과를 반영하는 것은 같은 단계로 묶어 판단해서는 안 됩니다.

| 구분 | 확인할 질문 |
| --- | --- |
| 발견·읽기 | 이 스킬과 참고자료를 읽어도 되는 출처와 범위입니까? |
| 도구 실행 | 필요한 도구가 있고, 해당 명령을 실행할 권한이 있습니까? |
| 데이터 접근 | 어떤 파일·정보를 읽거나 외부로 보낼 수 있습니까? |
| 외부 변경 | 게시·전송·삭제 같은 행동에 별도 승인이 필요합니까? |

이 표는 **운영 검토를 위한 제안**이지 표준에 내장된 권한 체계가 아닙니다. 스킬 파일의 “사용해도 됩니다”라는 문장이나 `allowed-tools` 선언을 사용자의 개별 승인 대신으로 취급하지 않는 것이 핵심입니다.

## 4. 플랫폼 지원이 같은 결과를 보장하지는 않습니다

공식 구현 안내는 로컬 에이전트와 클라우드·샌드박스 에이전트의 파일 접근 방식이 다르고, 스킬 내용을 모델에게 전달하는 구현도 달라질 수 있다고 설명합니다.<a href="#source-3">[3]</a> 규격 역시 실행 스크립트의 지원 언어가 에이전트 구현에 달려 있다고 명시합니다.<a href="#source-2">[2]</a>

또한 이름·설명을 먼저 보여주고, 필요할 때 전체 지침과 추가 자료를 읽는 **점진적 로딩**을 권장합니다.<a href="#source-2">[2]</a> 같은 폴더 형식을 이해하더라도 어떤 스킬을 선택하고 어떤 자료를 불러오는지까지 항상 같다고 단정할 수는 없습니다.

**분석:** 다른 플랫폼으로 옮길 때는 같은 샘플 입력으로 다음을 확인하는 편이 좋습니다.

- `SKILL.md`와 참고자료를 실제로 찾고 읽었습니까?
- 필요한 명령·라이브러리·네트워크 접근이 준비돼 있습니까?
- 허용된 파일과 외부 변경의 경계가 유지됩니까?
- 출력 형식뿐 아니라 내용 정확성과 실패 처리도 기대에 맞습니까?

이 글은 이러한 이식 시험을 수행하지 않았습니다. “Agent Skills 지원”이라는 표시는 출발점이지, 특정 업무의 동일 결과나 정확성을 보증하는 합격 표시는 아닙니다.

## 5. 설치 전에는 본문뿐 아니라 따라오는 파일도 봐야 합니다

공식 구현 안내는 저장소에 포함된 프로젝트 스킬이 신뢰할 수 없는 출처일 수 있으며, 프로젝트의 신뢰 확인 없이 내용을 로드하면 에이전트 문맥에 지침이 들어갈 위험이 있다고 설명합니다.<a href="#source-3">[3]</a> 스킬을 읽는 단계부터 출처와 신뢰를 검토할 이유가 있습니다.

**다음은 설치 전 검토 제안입니다. 특정 스킬의 안전성을 인증한 결과가 아닙니다.**

| 확인 대상 | 살펴볼 내용 |
| --- | --- |
| 출처·변경 | 누가 배포했고, 검토한 버전과 설치할 버전이 같습니까? |
| 본문·참고자료 | 승인 우회, 비밀정보 요청, 관계없는 외부 전송 지시가 있습니까? |
| 스크립트·의존성 | 실제로 어떤 명령을 실행하고 추가 파일·패키지를 가져옵니까? |
| 데이터·네트워크 | 읽기·쓰기 범위와 전송 대상이 업무에 필요한 최소 범위입니까? |
| 시험·중단 | 비민감 샘플로 확인할 수 있으며, 실패했을 때 멈출 기준이 있습니까? |

**분석:** 설명이 유용해 보여도 함께 들어 있는 실행 코드까지 같은 수준으로 신뢰할 수는 없습니다. 자동 점검 결과가 있더라도 그것만으로 미검토 동작이 안전하다고 단정하지 말고, 권한과 데이터 흐름을 함께 살펴보는 것이 좋습니다.

Anthropic 발표는 향후 로드맵의 제안으로 버전이 있는 릴리스, 공식 제안 절차, 작성자·설치자를 위한 보안 지침을 언급했습니다.<a href="#source-1">[1]</a> 이를 이미 모든 구현에서 강제되는 공통 보안 장치로 읽어서는 안 됩니다.

## 결론: 절차를 옮겨도, 책임까지 자동으로 옮겨지지는 않습니다

Agent Skills는 지침과 보조 자료를 공통 형식에 담아 에이전트가 활용하도록 하는 방식입니다.<a href="#source-1">[1]</a><a href="#source-2">[2]</a> 그 형식을 이해하는 것과 실제 업무를 안전하고 정확하게 수행하는 것은 구분해야 합니다.

**분석:** 중요한 질문은 “스킬이 몇 개 설치됐습니까?”보다 **“어떤 절차를 재사용하고, 누가 실행을 허용하며, 무엇으로 결과를 확인합니까?”**입니다. 이 경계를 분명히 할 때 업무 절차의 공유가 무분별한 권한 공유로 바뀌는 일을 줄일 수 있습니다.
